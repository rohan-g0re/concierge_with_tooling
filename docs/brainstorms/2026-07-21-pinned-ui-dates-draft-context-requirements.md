# Pinned Chat Chrome, Date-Aware Catalog, Conversational Draft Switching

## Problem Frame

Compass guests planning a cruise hit four friction walls: (1) the drafts panel and message composer scroll away with long chats, so guests lose sight of saved work and the ability to type; (2) the catalog has no sailing dates, so the single most common real-world constraint ("October", "back before Dec 28") cannot be answered; (3) when a query has no exact match, the assistant dead-ends instead of offering labeled alternatives; (4) referencing an earlier draft ("back to the dinner options in Alaska") triggers a comparison table or confusion instead of simply switching the conversation's context to that draft. Guests routinely hold multiple drafts of the *same* region or even the same cruise at different dates, so drafts need richer identity than a region name.

Seed: `docs/ideation/2026-07-21-pinned-ui-dates-draft-context-ideation.md`.

## Requirements

**A. Pinned Chat Chrome**
- R1. The drafts panel (DraftRail) stays fully visible at all times regardless of chat scroll position. If drafts exceed panel height, the panel's card list scrolls internally; panel header/footer stay fixed. No chat scrolling is ever needed to see or click a draft.
- R2. The message composer stays anchored at the bottom of the viewport at all times, regardless of chat scroll position. The guest can type from anywhere in the conversation history.

**B. Date-Aware Catalog**
- R3. Every cruise carries a sailing series: a list of concrete departure dates, each with a computed return date (departure + nights). One catalog entry per cruise; multiple sailings per entry.
- R4. Catalog expands from 4 to 6 regions: existing Alaska, Mexico, Caribbean, Mediterranean plus **Hawaii** (longer 10–15-night sailings) and **Bermuda/Bahamas** (short 5–7-night sailings). Roughly 30–40 cruises total, each with a multi-month sailing series.
- R5. Sailing series are generated by a repeatable seed script (realistic cadence, e.g. weekly/biweekly over ~6 months) rather than hand-authored per date.
- R6. Cruise result tiles shown in chat display one context-matched sailing (departure and return): if the query carried a date constraint, the sailing that satisfies it; otherwise the next upcoming departure. Extend the existing result tile component — no new tile variant unless the existing one cannot accommodate the fields.

**C. Date Filtering and Near-Miss Alternatives**
- R7. The guest can filter cruises by date constraints in natural language: month ("all October sailings"), return-by ("back before Dec 28"), duration ("14-day"), and combinations ("14-day returning before Dec 28"). Results reflect real sailing dates, including return dates.
- R8. When exact matches exist, they are always shown first and are never replaced by alternatives.
- R9. Below exact matches, the assistant proactively offers clearly-labeled near-miss alternatives that fall outside the stated constraint (e.g. a 7-day option alongside "14-day" requests, a 9-night option when the guest said "more than 10 nights", or ±7-day date shifts). The labeling must explicitly mark these as outside the stated constraint, offered for extra visibility — never presented as if the constraint was ignored. Exact label copy is decided in planning; labels are supplied by the tooling and rendered verbatim (see R11).
- R10. When zero exact matches exist, the assistant does not dead-end: it states there are no exact matches and shows the closest relaxed alternatives (nearby duration, nearby dates, other regions with matching dates).
- R11. Near-miss/relaxation logic is deterministic (computed in the search tooling), not left to the model's discretion; the model presents what the tool returns, including section labels, verbatim. Date/duration filter intents must invoke the search tooling via an explicit system-prompt rule (same pattern as the existing COMPARE DRAFTS rule) — prose-only answers to filter queries are forbidden.

**D. Draft Identity and Pricing**
- R12. Each draft is anchored to a specific cruise **and** a specific sailing (departure + return date), so multiple drafts of the same cruise at different dates are distinct. The sailing is fixed at cruise selection: the guest confirms or changes the tile's context-matched sailing when selecting the cruise, so every draft is born with a date — no draft ever exists without one. The sailing can be changed later in conversation.
- R13. The draft context available to the assistant includes, per draft: cruise name, region, embark port, departure date, return date, nights, and the **draft-held total** (base fare plus accumulated add-ons — e.g. $3,300 after add-ons, not the $3,000 catalog base).
- R14. The catalog remains the source of truth for base price; the draft holds its own evolving total. When talking about a draft, the assistant quotes the draft-held total, not the catalog base. When discussing a cruise that has no draft yet, the assistant quotes the catalog base price — it must never invent a draft-held total. The draft panel tile shows the draft-held total.

**E. Conversational Draft Switching**
- R15. When the guest references an existing draft in conversation (by cruise name, region, date, duration, price, or any distinguishing attribute — "the 7-day Alaska one", "the one starting 3rd August"), the assistant switches the active draft context and continues the conversation about that draft. It does NOT show a comparison table for single-draft references. Switching triggers on intent to discuss or modify that draft — not on incidental mentions ("my friend loved the Caribbean last year" must not switch or search).
- R16. The drafts panel visually reflects every context switch: the newly active draft is highlighted (and brought into view if the list scrolls), whether the switch was conversational or from a click.
- R17. When the guest's reference genuinely matches 2+ drafts (e.g. "the Alaska one" with three Alaska drafts and no distinguishing detail), the assistant asks "which one?" and shows the candidate drafts as tappable cards (name, sailing dates, nights, draft-held price). Tapping one performs the switch.
- R18. When the guest references a cruise or region with no matching draft, the assistant falls back to a fresh catalog search for it (the normal start-of-funnel flow) — no error, no ghost draft.
- R19. Clicking a draft in the panel continues to switch the active draft (existing behavior preserved); conversational switching is additive.

## User Flow — Draft Reference Resolution

```mermaid
flowchart TB
    A[Guest references a cruise/draft in chat] --> B{Matches existing drafts?}
    B -- exactly one --> C[Switch active draft]
    C --> D[Panel highlights that draft; conversation continues about it]
    B -- two or more --> E[Ask "which one?" + candidate draft cards]
    E --> F[Guest taps a card] --> C
    B -- none --> G[Fresh catalog search for the referenced cruise/region]
```

## Success Criteria

- Scrolling to the top of a long chat: drafts panel and composer both remain fully visible and usable.
- "Show me all October Alaska sailings" returns real dated results with departure and return dates.
- "14-day cruise returning before Dec 28" returns exact matches first, then labeled shorter/alternative options below — the exact-match section is never polluted or replaced.
- A query with zero matches produces closest-alternative suggestions, never an empty answer.
- With three Alaska drafts: "the one starting 3rd August" switches directly; "the Alaska one" produces a which-one card; "back to the dinner options in Alaska" (only one Alaska draft) calls `set_active_draft` with the correct draft id, the panel highlights that draft, and the dining conversation continues without re-asking which draft — no comparison table, and no prose-only "switch" that leaves the active draft unchanged.
- A draft with $300 of add-ons on a $3,000 cruise is always quoted at $3,300 in conversation and on its panel tile.

## Scope Boundaries

- No persistent storage — in-memory sessions + sessionStorage mirror stay as-is.
- No real inventory/availability integration; no checkout re-validation.
- No new voice transport work — the existing Realtime → /action relay carries tool calls unchanged. System-prompt and tool-definition changes required by R15/R17 are in scope and apply to both text and voice paths.
- No itinerary/ports-of-call expansion beyond what exists.
- Catalog price (`fare_now`) does not fluctuate; only draft-held totals diverge from base via add-ons.
- Comparison tables remain available but only for explicit comparison intents (existing COMPARE DRAFTS behavior unchanged).

## Key Decisions

- **Sailing series per cruise** (one entry, many dated sailings) over one-entry-per-date: preserves cruise identity, supports same-cruise/different-date drafts, keeps catalog compact. (User-selected.)
- **New regions: Hawaii + Bermuda/Bahamas** — chosen to widen the duration spectrum (5–7 and 10–15 nights), which gives the near-miss engine real material. (User-selected.)
- **Rich-identity-first disambiguation**: guests naturally give distinguishing details ("the 7-day one"); the assistant resolves against rich draft identity. Only genuinely ambiguous references trigger a which-one card. (User-directed.)
- **Deterministic near-miss logic in tooling**, not model discretion — documented Gemini-flash freeloading pattern makes prompt-only enforcement unreliable.
- **Alternatives never replace exact matches** — explicit user requirement; mislabeling alternatives as results is the exact failure being fixed.
- **Sailing chosen at cruise selection** — draft is always born with a date; avoids a new funnel step and dateless drafts. (User-selected.)
- **Tiles show one context-matched sailing** — the sailing that satisfies the query's date constraint, else next departure. (User-selected.)

## Dependencies / Assumptions

- Draft switching machinery (`set_active_draft` tool + /action bridge + panel click) already exists and works; this work extends when/how it is invoked and what identity data surrounds it.
- Per-turn session snapshot injection is the established mechanism for giving the model draft context; R13 extends its content.
- Seeded sailing dates are synthetic demo data; realism (cadence, seasonality) matters more than accuracy.
- Known pre-existing bug to fix during implementation: `backend/app/routers/action.py` reads `result.get('cruises')` for search results, but the search tool returns a `results` key — /action-path searches silently render empty.
- The expanded per-draft snapshot (R13) grows each paid Gemini turn; planning should size it against the existing per-turn cost caps before committing the field set.
