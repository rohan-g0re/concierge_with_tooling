# Compass — Conversational Cruise Concierge

**Meridian Line** is a premium cruise line demo. Compass is its booking experience: a conversational agent that renders real UI components inside the chat — cruise tiles with live sailing dates, fare pickers, itinerary views, comparison tables, and checkout handoff — instead of directing guests through a multi-page filter funnel.

---

## The problem with incumbent cruise booking

Holland America Line and Seabourn (both Carnival Corporation brands) use a classic e-commerce model: search form → results grid → 6–8 step checkout. That model has a structural ceiling:

- **No session memory.** A half-planned trip lives in browser tabs and the guest's head. Return a week later and start over.
- **Comparison is manual.** Want to weigh an Alaska sailing against Bermuda? Open two tabs and toggle.
- **Hard filters create dead ends.** "14-night cruise returning before Dec 28" returns zero results. The site offers nothing.
- **Anything nuanced requires a phone concierge.** Add-on pricing, itinerary questions, switching between options mid-planning — none of it is self-serve.

Compass closes that gap without replacing the booking engine; it changes what happens before the guest gets there.

---

## What Compass does differently

### One conversation holds the whole planning session

The guest types naturally — "show me Alaska in October," "what's included in the fare?", "back to the dinner options on that 12-night cruise." The agent maintains full context. There is no back button, no session timeout that loses the draft, no re-entering the same search.

### Chat that renders UI, not walls of text

Tool results return typed component descriptors. The frontend renders them via a registry map: cruise tiles with real sailing dates, fare/stateroom/dining/land-tour selection steps, per-night and total pricing, comparison tables across drafts, a checkout handoff card. The agent never describes a cruise in prose when a card can show it.

### Multiple parallel drafts, conversational switching

Guests can hold up to five active booking drafts simultaneously — different itineraries, different regions, different sail dates — and move between them by referring to them naturally. "The Alaska one starting in August" switches context and continues the conversation. "The Alaska one" with two Alaska drafts produces a "which one?" card with tappable candidates; one tap resolves it. Incidental mentions ("I've been to Alaska before") do not trigger a switch. Draft identity is unambiguous: UUID-keyed, session-snapshotted per turn.

### Date-aware catalog with deterministic near-miss alternatives

Every cruise in the catalog has a sailing series — departure and return dates generated by a repeatable seed, covering ~6 months of realistic cadence. Date constraints ("October," "returning before Dec 28," "14 nights") are parsed and passed to the search tool, which runs deterministic matching logic — not model discretion. Exact matches always appear first. Where constraints can't be met exactly, labeled near-miss alternatives appear below, explicitly marked as outside the constraint with the reason. The guest is never shown an empty state and never silently given a different result than they asked for.

### Draft-held pricing, not catalog base

Each draft anchors to a specific cruise and a specific sailing at selection. Add-ons update the draft-held total. When a draft exists, the agent quotes that total — never the catalog base price, never an invented number. The system prompt enforces this as a hard rule; the model cannot fabricate a draft-held total.

### Voice parity

The same booking funnel runs over voice via an OpenAI Realtime relay. Tool calls made in voice turns are bridged back through the same `/action` endpoint; the frontend renders the same components.

## Demo flows

Three rehearsed flows cover the core experience. Steps are composable — they mix and recombine across flows.

### Flow A — "October in Alaska"

Search → date-filtered results → select tile (creates draft, anchors to sailing) → fare package chip → pricing question (agent quotes draft-held total) → itinerary view → conversational aside (no tool call) → "Book it" → checkout handoff card.

**What to watch for:** The agent quotes draft-held total after the fare chip, not catalog base. The handoff card deep-links directly to checkout with draft state intact.

### Flow B — "Back before Dec 28"

Return-by constraint search → exact matches first, near-miss alternatives below with labels → select tile (Draft 1) → 20-night option (no exact match → labeled alternatives, not empty) → Bermuda search → select tile (Draft 2) → single-draft reference switches context directly, no compare table → explicit comparison request fires `compare_drafts` → per-night pricing from drafts, not catalog.

**What to watch for:** The labeled near-miss sections — the distinction between "here's what you asked for" and "here's the closest we have" is visible and explicit. Constraint reset: when the guest switches regions, stale filters are cleared.

### Flow C — "The Alaska Juggler"

Three drafts built across two regions (7-night Alaska, 12-night Alaska, Mexico) → "the Alaska one" triggers a disambiguation card → tap selects 7-night → dining question on 12-night uses `set_active_draft` (no disambiguation, different nights disambiguate) → incidental Caribbean mention does NOT trigger search or switch → hover-delete Mexico draft → Hawaii search (draft count stays at 2) → conversational recommendation closes the session without a checkout tool call.

**What to watch for:** The disambiguation card is triggered by genuine ambiguity, not by any mention of a region. The agent correctly distinguishes "which draft do you mean" from "which cruise should I pick."

## Architecture

Next.js 14 (App Router, TypeScript, Tailwind) frontend; FastAPI (Python 3.11) backend; Gemini function-calling agentic loop with tool-layer determinism (search, near-miss logic, and pricing computed in tools — not generated in model prose); stub mode for keyless demos (`LLM_MODE=stub`); voice parity via OpenAI Realtime WebRTC relay with tool bridging through `/action`. Session state is in-memory server-side with sessionStorage mirror on the client.
